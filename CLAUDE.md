# CLAUDE.md

Правила для агента, работающего над расчётно-пояснительной запиской (РПЗ) по курсу «Высокие нагрузки» НИУ ВШЭ.

## Контекст проекта

- РПЗ оформляется в `README.md` в корне репозитория, на русском.
- Тема: публичная AI-платформа (LLM-сервис уровня ChatGPT/Claude) с двумя каналами — веб-чат и HTTP API.
- Требования к разделам: `requirements/homework_architecture.md`. Это источник истины по структуре, всегда сверяйся.
- Эталонные работы: `example/music_streaming.md` и `example/telegram-clone-chat-main/README.md`. Там — целевая плотность, стиль и уровень детализации.

## Дисциплина данных

### Источники иерархии

1. **Официальные метрики издателя** (OpenAI announcements, отчёты компаний) — приоритет. Цитируй точную формулировку: «X токенов/мин», а не «X токенов/день».
2. **Индустриальные датасеты** (LMSYS-Chat-1M, WildChat, ShareChat, OpenRouter) — для размеров сообщений и поведения.
3. **Замеры DevTools/токенайзером** — для протокол-level фактов (байт/токен, JSON-overhead).
4. **Обоснованные оценки от лимитов** — последнее средство, с явным выводом (например, «лимит 20 МБ + типичный микс → ~5 МБ среднее»).

Запрещено: similarweb.com как первоисточник (требование курса).

### Web vs API — два разных профиля нагрузки

Это самая частая ошибка. Web и API нельзя усреднять или делить по DAU:

- **Web**: массовая аудитория живых людей, ~7 коротких промптов/день, ~800 токенов/запрос.
- **API**: небольшая когорта клиентов (сервисы/боты), сотни-тысячи запросов/день, ~6 400 токенов/запрос (полный контекст в каждом запросе).

Не вводи допущения вида «85% Web / 15% API» — выводи нагрузку напрямую из публикуемых издателем метрик отдельно для каждого канала.

## Формат

### Заголовки

- Все подразделы внутри секции — одного уровня (`##` для глав, `###` для подразделов). Не используй `**bold**` как заголовок и не переходи внезапно на `###` посреди `##`-секции.

### Источники

- Все ссылки — в виде `[^N]` сносок. Сводный список — в самом конце документа, под `# Источники`.
- Каждое числовое утверждение, не выведенное расчётом, должно иметь источник.

### Таблицы vs проза

Таблицами оформляем (как в `example/telegram-clone-chat-main/README.md`):

- продуктовые метрики (MAU/DAU/действия/...);
- параметры расчёта (значение + источник/формула);
- размеры данных, RPS, сетевой трафик;
- сводки по подсистемам.

Прозой пишем только то, что не сводится к таблице (обоснования архитектурных выборов, описание потоков).

### Расчёты

- Любая производная цифра должна сопровождаться формулой в строке таблицы или ниже.
- Формулы — в LaTeX (`$...$` / `$$...$$`) или fenced-block, как в примерах.
- Единицы конвертируй явно: «KB/s × 8 / 1000 = Gbit/s», не оставляй переход в уме.
- Округляй до чистых чисел, если число всё равно произвольное (1 млрд vs 950 млн — выбирай 1 млрд).

### Стиль текста

- Кратко и по делу, как в эталонных работах. Если можно убрать абзац без потери смысла — убирай.
- Не добавляй «капитанские» комментарии вроде «это очень важно» или «как мы видим».
- Не пиши пустых ячеек-заглушек в таблицах («от 10 до миллионов» — это не значение, это отсутствие значения; такие строки удаляй).

### Простые термины

Стремимся к самому простому слову, которое корректно описывает явление. Перед тем как ввести термин — проверь:

1. **Есть ли общеупотребимый русский / родовой эквивалент?** Используй его. `north-south traffic` → `внешний трафик`, `east-west traffic` → `межсервисный`, `cold path` → `редкие запросы`, `warm replica` → `горячая реплика`, `quorum read` → `чтение с кворумом», `tail latency` → `задержка хвоста распределения (p99)».
2. **Если ввёл англицизм — расшифруй в скобках при первом упоминании.** `backpressure (сигнал «притормози, я перегружен» от downstream к upstream)`, `idempotency-key (ключ, по которому повтор того же запроса не приводит к двойной записи)`, `circuit breaker (автоматическое отключение неисправного зависимого сервиса)`.
3. **Не используй жаргон ради жаргона.** «Хвост распределения» понятнее, чем «tail latency»; «балансировка под слой L7» понятнее, чем «L7 load balancing» без определения L7. Если ввёл `L7` — рядом в скобках: «работает с HTTP-заголовками».
4. **Если термин нужен по делу (industry-standard, на защите спросят) — оставляем, но один раз расшифровываем.** `BGP`, `Anycast`, `TLS termination`, `gRPC server-streaming`, `continuous batching`, `materialized view` — всё это нужно, но при первом появлении объясняем одной строкой.
5. **Сложные «облачные» термины без on-prem-аналога — заменяем родовым.** `availability zone` → `зона отказа`, `region` → `регион / ДЦ`, `edge` → `граница сети`, `origin` → `обратный конец / приложение».

Простое правило: если читатель РПЗ — препод-сетевик-широкого профиля, ему не должны мешать незнакомые слова. Каждое незнакомое слово при первом появлении — в скобках расшифровка одной строкой.

### Buzzword-дисциплина

Препод гоняет на защите по любому термину, который ввёл студент. Поэтому правила:

1. **Не используй термин, если не готов объяснить его в одном предложении на защите.** «Anycast CDN», «Geo Steering», «BGP route announcement», «service mesh», «sidecar proxy» — слепили из нескольких концепций, на защите их разворачивать; либо упрощай, либо объясняй родовыми словами в самом тексте.
2. **Слепленные buzzword-ы запрещены.** «Anycast CDN» — два слова в одно, непонятно что внутри. Anycast (как сетевую технику) использовать можно, но в тексте сначала ввести **в одном предложении**: «Anycast — один IP анонсируется из нескольких ДЦ через BGP, сеть направляет пакет в ближайший ДЦ». Дальше можно говорить просто «Anycast». То же самое с «Geo Steering» — заменяй на родовое «weighted L7 routing» или «routing policy с фолбэками».
3. **Названия вендоров (Cloudflare, AWS Route 53, GCP Cloud Load Balancing) — только если архитектура реально на нём завязана и студент готов защищать выбор.** По умолчанию пиши родовое: «Anycast IP», «L7-балансировщик», «managed L4 LB», «edge cache». Не говори «Cloudflare Workers», говори «L7-edge с canary через header-matching».
4. **Если есть и простой, и сложный примитив с тем же эффектом — выбирай простой.** GeoDNS вместо Anycast выбирай только если у тебя нет требований к sub-100ms failover. Anycast — оправдан, когда нужна сетевая маршрутизация на единый IP с failover за секунды.
5. **Buzzword без числа — индикатор bullshit.** Если ввёл «горизонтальное масштабирование» — покажи число шардов / реплик. Ввёл «failover» — покажи RTO / RPO. Ввёл Anycast — покажи число ДЦ и схему маршрутизации.

### Sanity-checks

- Сумма по каналам = итог: `Web RPS + API RPS == Total RPS`.
- Concurrent SSE = peak RPS × средняя длительность ответа (Little's Law).
- Пиковый множитель ×2 применяется один раз — не суммируй два раза, не забывай при расчёте инфраструктуры.
- Прямой upload в S3 (если решено архитектурой) **не** идёт через Nginx — исключай из L7 sizing.

## Подсказки по разделам

### §2 (Расчёт нагрузки)

Минимально должно быть:
- MAU, DAU (с расчётом из WAU/MAU sticky factor);
- разделение по каналам с RPS avg/peak;
- среднее количество действий на пользователя (для Web; для API — оговорка про суммарный счёт);
- размер сетевого payload (input/output отдельно);
- хранилище на пользователя (по типам данных);
- общий объём хранилища за год;
- concurrent connections (для streaming-сервисов);
- сетевой трафик (incoming/outgoing peak Gbit/s + суточный);
- сводная таблица RPS по типам запросов.

### §3 (Глобальная балансировка)

§3 — **только про маршрутизацию запросов между ДЦ**. Не путай со «схемой одного запроса». Туда не входит:

- архитектура inference (control plane / data plane, gRPC, очереди задач) — это §7 «Алгоритмы» / §10 «Схема проекта»;
- мультимодальный pull-flow (presigned URL, S3→GPU) — туда же;
- размещение stateful-сервисов (Rate Limiter, Billing) — упомянуть одной строкой в §3.3, детали в §6;
- финальная «итоговая» схема, которая дублирует §3.3 — удаляй.

Минимально достаточный §3 (5 подразделов; покрывает все «при наличии»-пункты из `requirements/homework_architecture.md` §3):

1. **§3.1 Разбиение по доменам** — таблица DNS-доменов (`chat.*`, `api.*`, `cdn.*`, ...) + одна строка про общий Anycast IP.
2. **§3.2 Расположение ДЦ + обоснование** — таблица регион → город → роль + 3 буллита «почему столько ДЦ» (с числовым обоснованием граничных вариантов: 1 ДЦ, 4 ДЦ, >4 ДЦ) + 1 абзац про распределение GPU + таблица влияния на продуктовые метрики (3–5 строк, **только понятные**: TTFT, доступность, стоимость; никаких «conversion +1–3%», «GDPR compliance», если это не входит в MVP).
3. **§3.3 Распределение запросов по ДЦ** — таблица RPS / SSE по регионам; числа берутся прямо из §2; явная формулировка «эти числа — вход для §4 (сколько Nginx)»; per-region vs централизованные state-сервисы — одной строкой каждый. Лишние колонки («Inference origin», если она не несёт нового смысла) — удалить.
4. **§3.4 Anycast-балансировка** — DNS-балансировки в нашей схеме нет (одной строкой про резолв в общий IP), всё делает Anycast. Mermaid сетевой маршрутизации + что такое Anycast в одном предложении (BGP, один IP, ближайший ДЦ) + 4 буллита «что мы получаем» + параметры DNS (TTL, NS, DNSSEC).
5. **§3.5 Регулировка трафика между ДЦ** — в начале явно: «это про балансировку **между ДЦ**, балансировка **внутри** одного ДЦ — §4». Таблица условий снятия региона из ротации (latency p95 / error rate / origin pool / GPU queue), routing policy с fallback, 3 способа переключения.

Если DNS-балансировка реально есть (GeoDNS) — выноси в отдельный §3.4, и Anycast — в §3.5. У нас её нет → объединяем.

Целевой объём — 120–160 строк. Если уехал за 200 — режь. Если короче 80 — недотянул, не хватает обоснований.

### Граница «глобальная (§3) vs локальная (§4)»

- **Глобальная (§3)** = маршрутизация **между ДЦ**. Объекты — целые ДЦ, регионы. Решения — «в какой ДЦ отправить пакет», «какой ДЦ снять с ротации».
- **Локальная (§4)** = маршрутизация **внутри одного ДЦ**. Объекты — Nginx-ноды, K8s-pods, upstream-инстансы. Решения — «на какой Nginx из 10», «на какой Pod из 50», health-check между Nginx и upstream.

Если в §3 описывается алгоритм для отдельных нод/Pod-ов — это §4.
Если в §4 описывается переключение между ДЦ — это §3.

### Defense cheat-sheet (устная защита)

**`notes/defense-cheatsheet.md`** — отдельный артефакт, **не** часть РПЗ. Туда складываем:

- Контр-аргументы на возможные вопросы препода («а почему не X?», «а зачем Y?»).
- Развёрнутые обоснования, которые в РПЗ пишутся в одну строку, но на защите хочется иметь под рукой.
- Альтернативы, которые мы рассмотрели и отвергли, с краткой аргументацией.

Не путать с drafts-файлами:

| Файл | Что туда идёт | Что с этим будет |
|------|---------------|------------------|
| `notes/section-7-10-drafts.md` | Архитектурные куски, рождённые в одной секции, но по смыслу относящиеся к §7/§10 | **Переедут** в РПЗ при заполнении §7/§10 |
| `notes/section-11-drafts.md` | Серверы / контейнеры / cross-DC backbone — для §11 | **Переедут** в РПЗ при заполнении §11 |
| `notes/defense-cheatsheet.md` | Контр-аргументы, расширенные обоснования, альтернативы | **Останутся** только в шпаргалке для устной защиты |

Когда выносишь блок в `defense-cheatsheet.md` — оставляй в README HTML-комментарий-маяк (`<!-- ... в notes/defense-cheatsheet.md -->`), чтобы при следующей правке агент видел, что блок не потерян, а сознательно перенесён.

**README — итоговый документ.** В нём не должно быть видимых упоминаний:
- `notes/`, `defense-cheatsheet`, `section-7-10-drafts`, `section-11-drafts` — ни в тексте, ни в Mermaid-диаграммах, ни в таблицах;

Каждый абзац в РПЗ должен отвечать на конкретное требование из `requirements/homework_architecture.md`; если ответ можно дать таблицей — пишем таблицу, не прозу.

### §4 (Локальная балансировка)

Расчёт балансировщиков должен иметь **минимум два ограничителя**: пропускная способность сети и SSL/TLS termination (CPS). Используй источники [`blog.nginx.org`](https://blog.nginx.org/blog/testing-the-performance-of-nginx-and-nginx-plus-web-servers) и [`blog.nginx.org/.../nginx-ingress-controller-kubernetes`](https://blog.nginx.org/blog/testing-performance-nginx-ingress-controller-kubernetes) — они в требованиях курса.

### §5/§6 (БД)

- В логической схеме (§5) указывай размер строки, QPS чтения/записи, требования к консистентности, особенности распределения ключей.
- **§5 — database-agnostic.** Никаких упоминаний Redis, PG, Scylla, ClickHouse в карточках таблиц. Поля `(внутри Hash)`, «Redis-ключ», «в RAM» — всё это §6. Тот же принцип для алгоритмов хранения и репликации.
- В физической схеме (§6) — конкретную СУБД с обоснованием, индексы, шардирование, репликацию, бэкапы.
- Не теряй сущности: файлы/blob-данные (Ceph RGW / S3), кэши (Redis), очереди — всё это часть БД-картины.

### Версионируемые справочники (tier, model, …)

- Справочники с **бизнес-атрибутами** (цены, лимиты) делаем **версионируемыми**: PK — UUID, плюс поле `effective_to TIMESTAMP NULL`.
- При смене цены/лимита: INSERT новой строки с новым UUID + UPDATE старой `effective_to = NOW()`. Запрещено UPDATE-ить атрибуты «на месте» — это сломает исторические `usage_records`, ссылающиеся на этот ID.
- Human-readable код (`tier_code`, `model_code`) — обычный VARCHAR-атрибут, **не PK**. У одного кода может быть несколько ценовых версий. Для lookup «текущая версия по коду» — partial-индекс `WHERE effective_to IS NULL`.

### Multi-currency

- MVP — только USD. Поля `currency` в `billing_accounts` и `price_*` в справочниках — без указания валюты.
- Multi-currency требует отдельного FX-rates-сервиса и conversion-time pricing с аудитом — это самостоятельный модуль, не часть базовой схемы.

### Объектное хранилище

- Целевое хранилище blob-данных — **Ceph RGW** (self-hosted, S3-compatible). Поля `s3_bucket` / `s3_key` сохраняем — это нейминг S3 API.
- Managed AWS S3 не подходит на нашем объёме (десятки ПБ/год): стоимость хранения и egress сопоставима с GPU-парком. MinIO исключён — основной репозиторий переведён в read-only в начале 2026.
- Erasure Coding (например, 8+3) предпочтительнее ×3 replication — overhead ×1.375 vs ×3 при сравнимой durability на наших объёмах.

2. **Физические проекции данных** — какие сущности обязаны лежать рядом (по образцу telegram-clone: chat-centric / user-centric). Это объясняет, почему shard key у разных таблиц разный.

6. **Бэкапы** с RPO/RTO.
7. **Сводная таблица** физической схемы.

**Правила для ScyllaDB/Cassandra-style:**

- Различай `Partition Key` (определяет ноду) и `Clustering Key` (порядок строк внутри партиции). В таблице полей помечай оба.
- Запрещай в API запросы без partition key (full scan по всем партициям — антипаттерн, явно указывай).
- Объясняй формат clustering key (DESC vs ASC, tiebreaker — например, `(created_at DESC, message_id)`).
- Альтернативные точки доступа (например, по `request_id` при partition key `conv_id`) — через **Materialized View**, а не Secondary Index (последний даёт scatter-gather).

### ENUM vs справочник: критерий выбора

При появлении категориального поля проверяй по правилу **«есть ли у значения бизнес-атрибуты?»**:

| У значения есть атрибуты (цена, лимит, max_context) | Решение |
| --- | --- |
| Да (`tier`, `model`, `pricing_plan`) | **Справочник** в PG, FK по коду (`tier_code`, `model_code`). Single source of truth, изменения без миграции кода |
| Нет (`role`, `status`, `channel`, `finish_reason`) | **ENUM** (PG ENUM или CHECK), `LowCardinality(String)` в ClickHouse, TEXT в Scylla |
| Open-ended коды, добавляются кодом (`event_type`) | **VARCHAR** (PG) или `LowCardinality(String)` (CH) — справочник пришлось бы синхронизировать с релизами |

Антипаттерны:
- Тотальная нормализация всех ENUM-ов в lookup-таблицы — в Scylla убивает single-partition-read pattern (JOIN-ов нет), в ClickHouse дублирует то, что бесплатно даёт `LowCardinality`.
- Дублирование `tier` в нескольких таблицах (например, в `users` и `billing_accounts`) — один из них устареет, поле должно быть в **одной** таблице, FK везде. Биллинг хранит только деньги, тариф — на user.
- Хранение `tier_limit_rps` / `price_per_token` в каждой строке (вместо справочника) — UPDATE миллионов строк при изменении лимита/цены.

### Трассировка request → response в БД

Для inference-цикла (или любого многоэтапного запроса, который порождает 2+ записей в разных таблицах):

1. **`request_id`** (correlation ID) — UUID, генерируется на edge, идёт в `X-Request-ID` HTTP-header, кладётся **в каждую** связанную запись (`messages`, `usage_records`, `attachments`). Совпадает с `trace_id` в Tempo/Jaeger — даёт сквозной audit от HTTP до GPU worker.
2. **`parent_message_id`** (self-FK в `messages`) — `assistant.parent_message_id = user.message_id`. Закрывает regenerate, branching, edit. Без него «какой именно ответ на какой prompt» восстанавливается только эвристикой по `created_at`.
3. Lookup по `request_id` в Scylla — через **Materialized View** (`messages_by_request`); в ClickHouse — skipping index (`bloom_filter`); в PG — обычный B-tree.

Без этих полей цепочка «promtp → response» держится только на `(conv_id, created_at, role)` ordering — это ломается при race / regenerate / branching и не даёт audit «покажи мне всю обработку запроса X».

### Аббревиатуры и DB-термины: расшифровка при первом использовании

На защите ревьюер тыкает в **любой** непонятный термин. Поэтому:

1. **При первом использовании** аббревиатуры в тексте — даём расшифровку в скобках или одной строкой:
   - `RF` (Replication Factor), `RPO/RTO` (Recovery Point/Time Objective), `AZ` (Availability Zone), `HA` (High Availability), `WAL` (Write-Ahead Log), `GC` (Garbage Collection), `DR` (Disaster Recovery), `DWH` (Data Warehouse).
   - Универсальные (`API`, `URL`, `RPS`, `MAU`/`DAU`, `TLS`, `HTTP`, `JSON`, `UUID`, `TTL`, `SQL`) — не расшифровываем.

2. **DB-специфичные термины** — одна строка пояснения при первом упоминании:
   - `Murmur3` — hash-функция Cassandra/Scylla для partition routing;
   - `memtable + SSTable + WAL` — write path в Scylla (in-memory buffer → sorted disk file → durability log);
   - `LOCAL_QUORUM` — кворум только в локальном DC, не cross-DC;
   - `multi-DC keyspace` — schema-настройка Scylla для разного RF в разных DC;
   - `MergeTree / LowCardinality` — ClickHouse engine + словарное сжатие;
   - `wide-column` — семейство БД (Cassandra/Scylla): row + dynamic columns с partition+clustering ключами;
   - `scatter-gather` — распределённый fan-out на все шарды + сборка ответа (антипаттерн для OLTP);
   - `token bucket / sliding window` — rate-limit алгоритм;
   - `presigned PUT/GET URL` — S3 механизм временного доступа без AWS-кредов.

3. **Числа вместо vendor-специфичных терминов**:
   - `11-nines durability` → `99.999999999%` (явно).
   - `S3 Glacier` → `cold-storage tier` (если не вендор-критично).

4. **Не плоди новых сокращений** в тексте: один раз ввёл `RPO`, дальше можно использовать без пояснения; не вводи `XYZ-aware loadbalancer` без определения, чем именно он `XYZ-aware`.

## Структурная дисциплина

### Single source of truth

Каждый факт / число / таблица должны жить в **одном месте** документа:

| Артефакт | Единственное место |
|----------|--------------------|

Если что-то повторяется в двух местах — это **бага дисциплины**: при правке одного из них второй неизбежно отстанет. В таких случаях: оставляем только в одном месте, в другом — кросс-ссылку (`см. §X.Y`).

### Согласованность между подразделами

После любой правки подраздела (например, §3.X) обязателен прогон по соседним подразделам той же секции:

- Согласованы ли таблицы? Не разъехался ли столбец «Размещение / Назначение» в §3.1 vs DNS-таблица в §3.4? (Это реальная история — было.)
- Совпадают ли термины? Если в §3.4 ввели «Anycast IP» — в §3.5 не появилось ли вдруг «Anycast CDN»?
- Совпадают ли числа? Если в §3.3 итог `170 108 peak`, в §4 не должно быть `173 200` из старой версии.
- Корректны ли cross-refs (`см. §X.Y`) — не указывают ли на удалённые подразделы?

Это занимает 30 секунд через `Grep` по ключевым словам/числам, экономит часы потом.

### Логическая последовательность правок

Правила работы с большой секцией:

1. **Читай секцию целиком до начала правок.** Понимай, какую роль играет каждый подраздел.
2. **Не удаляй блоки в составе крупных StrReplace без явного намерения.** Если делаешь большую замену — выноси удаляемые блоки в отдельный StrReplace, чтобы видеть, что именно уходит.
3. **После каждой существенной правки — self-review:** перечитай раздел целиком как ревьюер. Найди дубли, расхождения, потерянные блоки.
4. **Перед переходом к следующей секции — итог:** короткое summary сделанного + список открытых висяков (зафиксировать в CLAUDE.md в «Известные висяки»).
5. **Не расширяй scope за рамки запроса.** Если правишь §3, а в §4 нашёл устаревшее число — фиксируй в висяках, не правь сходу. Иначе потеряется контекст текущей задачи.

### Минимально достаточный текст в РПЗ

РПЗ — формальный документ, не лекция. В нём:

- **Каждый блок защитим в одном предложении:** если ты не можешь объяснить блок одним предложением на защите — он либо лишний, либо неправильно структурирован.
- **Контр-аргументы и расширенные обоснования** — не в РПЗ, а в `notes/defense-cheatsheet.md`. В РПЗ — только основное обоснование одной фразой.
- **Альтернативы, которые рассмотрены и отвергнуты,** упоминаются только если их рассмотрение существенно для защиты решения. Иначе — в `defense-cheatsheet.md`.
- **«Полезное, но не обязательное»** — в notes, а не в РПЗ.

Простое правило: задайся вопросом «это нужно прочитать ревьюеру РПЗ, или это для меня на защите?». Второе — в notes.
